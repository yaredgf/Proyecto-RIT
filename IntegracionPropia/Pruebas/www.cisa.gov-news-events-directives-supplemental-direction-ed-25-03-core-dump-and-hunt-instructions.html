Core Dump and Hunt Guidance for Cisco Devices

Original Issuance Date: September 25, 2025

Updated April 24, 2026

Note: CISA updated this Supplemental Direction on April 23, 2026, to accommodate instructions for Cisco Firepower and Secure Firewall devices.

Emergency Directive (ED) 25-03: Identify and Mitigate Potential Compromise of Cisco Devices directs Federal Civilian Executive Branch (FCEB) agencies to identify, hunt for, update, and remediate in‑scope Cisco Adaptive Security Appliance (ASA), Cisco Firepower, and Cisco Secure Firewall devices. Exploitation activities linked to CVE-2025-20333 (remote code execution), CVE-2025-20362 (privilege escalation), and observed persistence mechanisms pose an unacceptable risk to FCEB information systems, necessitating immediate action to mitigate remote code execution, privilege escalation, and long‑term unauthorized access.

CISA is providing this Supplemental Direction to help organizations detect and eradicate persistence and harden affected Cisco devices. ED 25-03 requires FCEB agencies to implement the measures below—including core dump collection and analysis, patching, hard resets, and reporting—and to report any indications of compromise or unusual activity to CISA. Though Emergency Directives apply only to federal agencies, CISA strongly encourages all organizations to use this guidance to reduce the risk surface of their networks.

Background

CISA is aware of an ongoing campaign by a sophisticated threat actor exploiting Cisco products exposed via web services, specifically:

  • Cisco ASA
  • Cisco Firepower products with ASA or Firepower Threat Defense (FTD) software
  • Cisco Secure Firewall products with ASA or FTD software

Note: CISA did not initially have evidence that the threat actor exploited Firepower and Secure Firewall devices when ED 25-03 was released in September 2025; however, this updated Supplemental Direction accompanies the updated ED due to evidence that now suggests exploitation of these devices.

The threat actor gains initial access to these devices by exploiting CVE-2025-20333 [CWE-862: Missing Authorization] and/or CVE-2025-20362 [CWE-120: Classic Buffer Overflow]. Cisco has released updates to address both CVEs, and the updates specific to these CVEs appear to successfully prevent initial compromise. However, CISA is aware of an advanced persistence mechanism—referred to as “FIRESTARTER” —that the threat actor uses on Cisco Firepower and Secure Firewall devices to persist through these updates. This mechanism remains on affected devices, enabling continued exploitation. The below guidance provides mitigations to address the FIRESTARTER persistence mechanism, as well as links to Cisco’s latest software release that also aims to mitigate the persistence.

Cisco ASA devices are not vulnerable to the FIRESTARTER persistence mechanism; however, they remain vulnerable to initial exploitation if unpatched.

Additionally, software versions after 9.17.1.40, 9.18.4.41, 9.19.1.32, and 9.20+ are not vulnerable to the overflow because the handler was removed. However, if a device previously ran a software version that predates these releases, it may still be compromised, even if it has since been updated.

This Supplemental Direction contains three main sections:

  1. Guidance for Cisco Firepower and Secure Firewall Devices With FTD Software
  2. Guidance for Cisco Firepower and Secure Firewall Devices With ASA Software
  3. Guidance for Cisco ASA Devices

It is imperative that organizations follow the correct guidance for each device category, as instructions and commands vary. If your device does not fall into these categories, no further artifact collection is required; proceed with the remaining steps in ED 25-03. If you are unsure about the hardware or software version of your device, use the “show version” command to determine the version.

Within each section, complete the steps in the exact order listed. Any deviation may trigger threat actor anti-forensics measures, which will destroy forensic data and disrupt ongoing investigations. To avoid activating threat actor anti-forensics measures:

  • Do NOT use the “tab” autocomplete or any other autocomplete function. The threat actor has hooked these commands to crash the device.
  • Do NOT take any remediation actions beyond what is described below (i.e., blocking IPs) without consulting with CISA first. The threat actor is closely monitoring for changes and can pivot rapidly to new infrastructure.

According to recent reporting, malicious activity likely began before or as early as 2024. For additional information related to this malicious activity, see:

  • CISA’s FIRESTARTER Backdoor Malware Analysis Report
  • United Kingdom National Cyber Security Centre’s RayInitiator & LINE VIPER Malware Analysis Report
  • The Cisco Talos Blog: FIRESTARTER

Note: This guidance reflects CISA’s current understanding of the threat. Related investigations are ongoing, and there are still unknown elements to the malicious activity. CISA encourages all organizations to report findings to CISA, especially if new malicious activity or detection methods are observed.

Guidance for Cisco Firepower and Secure Firewall Devices With FTD Software

The guidance in this section is specific to Cisco Firepower and Secure Firewall devices with FTD software. In conjunction with Cisco’s released guidance, use the steps below to collect artifacts, obtain and submit a core dump to CISA’s Malware Next Generation (MNG) platform, apply Cisco’s latest software updates, perform a hard restart, and conduct follow-on threat hunting.

A: Collect Device Artifacts
  1. Confirm Device Information

    Identify and document device model type, serial number, and firmware version.

  1. Run Initial Commands and Collect Output

    Before collecting a core dump, run the below commands in the FTD Command Line Interface (CLI). The output is crucial for analysis; CISA may request it at a later date. Save the output in a location off the device. If your device crashes as a result of running any command in this step (excluding the expected reload during core dump collection), stop all actions and contact CISA immediately.

    1. Access the FTD CLI.

      Note: FTD CLI access method varies by product and channel (Secure Shell [SSH] vs console).

      1. From the FTD CLI, execute the following commands:
        1. system support diagnostic-cli
        2. enable
    2. Run “show checkheaps” command.
      1. Record the time of the last successful checkheaps command shown in the output.
      2. Copy and save the full output off the device (preferably to an isolated system).
      3. Wait at least five minutes, then run “show checkheaps” again. Review the last row for “Total number of runs.”
        1. Expect an increase of approximately one per 60 seconds elapsed (i.e., if the command is executed five minutes apart, the number should increase by approximately five).
        2. Note the value and whether it increased.

      4. If there is no positive change in “Total number of runs,” this is evidence of a potential compromise.

        Note: The command output displays the following:
    3. Run “show tech-support detail” command.
      1. This command aggregates device information by running a broad set of show commands. From this output, make sure to capture:
        1. Uptime
        2. ROMMON version
        3. Firmware version
        4. Last crashinfo
      2. Save the full output off the device (preferably to an isolated system).
  2. Collect Core Dump

    Note: The steps below trigger an immediate reload of the device and may cause network degradation or outages.

    1. Soft reboot the device to maximize the likelihood of a clean core dump.
    2. Collect a core dump and save a copy.

      1. Follow model-specific instructions:

        1. For Firepower 1000/2100 and Secure Firewalls (all models), follow step 6 in the Cisco Firepower 1000/2100 Series Forensic Data Collection Procedures
        2. Firepower 4100/9300 follow step 7 in the Cisco Firepower 4100 Series and 9300 Series Appliances Forensic Data Collection Procedures

        Note: FCEB agencies should contact CISA if they encounter any issues.

    3. If nothing is written (i.e., no file appears in the file system):
      1. Record this condition.
      2. Review the command output for errors (i.e., “disk0: free space is too full to write a coredump.”)

      3. Run the commands again.

        1. If successful on the second attempt, inform CISA.
        2. If there is still no output, document and inform CISA; this may indicate an error or possible compromise.

        Note: Core dump files typically follow a naming pattern similar to: “core_1756308546_firepower_lina_11.3692.gz”

B. Upload Core Dump in CISA’s Malware Next Generation (MNG) Platform

To upload a core dump to CISA’s MNG platform, see the Annex below.

C. Apply Patch per CISA’s ED 25-03 and Cisco’s Security Advisory

After device artifact and core dump collection, apply Cisco’s latest software updates and consult the instructions in ED 25-03 and Cisco’s Security Advisory. These updates address:

  • CVE-2025-20333
  • CVE-2025-20362
  • FIRESTARTER persistence mechanism

To confirm the correct updated version (with the relevant hotfix), review the software tables included in Cisco’s Security Advisory. Ensure you notate which version you upgrade to, as this will need to be reported to CISA.

Note:

  • For Firepower 4100 and 9300 devices, entities must upgrade the Firepower eXtensible Operating System (FXOS) before upgrading the FTD software.
  • For Secure Firewall 3100 and 4200 devices in multi-instance mode, entities should consult Cisco’s Firewall Management Center, which provides guidance on upgrading FXOS and the FTD software.

After implementing the latest software updates:

  • If core dump results do not indicate compromise, proceed to step D (Perform a Hard Restart of Cisco Firepower and Cisco Secure Firewall Devices).
  • If core dump results indicate compromise, keep the device powered on, immediately disconnect the device from the network, and contact CISA for further guidance. Do not take any additional actions without coordinating with CISA.
D. Perform a Hard Restart of Cisco Firepower and Cisco Secure Firewall Devices

Note: If the core dump analysis indicates potential compromise, do not proceed with this section or take any additional action until coordinating with CISA.

CISA has determined that the only method to confidently remove the FIRESTARTER persistence mechanism is to physically unplug the device from its power source, forcing a hard restart. As a precaution, all organizations should take the below steps immediately after implementing the latest software updates, even if the core dump analysis does not indicate compromise. If an organization patches a device but cannot perform a hard restart immediately after, CISA recommends obtaining a new core dump and analyzing it for compromise before hard restarting.

To perform a hard restart:

  1. Locate physical device.

  1. While the device is running, physically unplug it from all power sources.

    Note: A standard reboot is insufficient. Fully remove power, including any redundant power sources.

  1. Leave the device fully disconnected from power for one minute.
  1. Reconnect power and allow device to boot.
E. Conduct Further Threat Hunting

If CISA’s MNG platform results show malicious indicators of compromise:

  • FCEB agencies should follow ED 25-03 and contact CISA immediately.
  • Other U.S. organizations should contact CISA via the Incident Reporting System or through CISA’s 24/7 Operations Center (contact@cisa.dhs.gov or 888-282-0870).
  • Cisco customers should open a Cisco Technical Assistance Center (TAC) case and include the output of the “show tech-support detail” command.

In conjunction with Cisco’s released guidance, use the steps below to detect additional malicious activity, as the threat actor may have pivoted from the compromised device to other areas of the network. Organizations do not need to complete these steps strictly in order; however, begin with identifying compromised user accounts, which has proven the most reliable starting point.

  1. Identify Compromised Accounts

    Begin by identifying potentially compromised accounts. Based on current investigations, one reliable method is monitoring and searching for impossible-travel logins; scrutinize all logins traversing the compromised device.

    1. Monitor and search for impossible-travel logins.

      1. Detect suspicious logins from geographically distant IP addresses using the following Splunk Search Processing Language (SPL) query (tailor it to the security information and event management [SIEM] solution in place):

        index=<NDR/Appliance> sourcetype=<log_source>

        | search event_type="authentication"

        | iplocation src_ip

        | stats earliest(_time) AS first_login latest(_time) AS last_login by user, src_ip, City, Country

        | where first_login != last_login AND distance_between(first_login_location, last_login_location) > 1000

        | table user, src_ip, first_login, last_login, City, Country

    2. Review syslog message IDs.
      1. Informational level:
        1. WebVPN session terminated: Idle Timeout : %FTD-6-716002

      2. Debug level:

        1. SVC Service Termination: %FTD-7-722029
        2. SVC Service Termination: %FTD-7-722030
        3. SVC Service Termination: %FTD-7-722031

        Note: Informational-level syslogs should be enabled by default; enable if disabled. Debug-level syslogs are not enabled by default; enable if feasible.

  1. Review Compromised Account Activity

    Monitor and search for the below known threat actor activities conducted after obtaining account access.

    1. Check for credential reuse.
      1. If a compromised device contains user or service account credentials (i.e., usernames and passwords), assess those accounts for lateral movement, especially where credentials are reused across the enterprise or follow predictable patterns (e.g., “Password12 > Password23”).
      2. If only account names (no passwords) are present, enable enhanced monitoring (i.e., login sources, actions performed) and review for suspicious activity.
      3. If a compromised device provides virtual private network (VPN) access, search for login attempts from the assigned VPN pool address and compare against all authentication sources, regardless of the account used.
    2. Check for credential harvesting.
      1. Run a “show capture” command to check for evidence of unauthorized packet captures configured to target:
        1. Terminal Access Controller Access-Control System Plus (TACACS+)
        2. Remote Authentication Dial-In User Service (RADIUS)
        3. Lightweight Directory Access Protocol (LDAP)
        4. Server Message Block (SMB)
      2. Determine whether shared keys between the compromised device and the centralized authentication server could enable decryption of captured traffic; if so, monitor for unauthorized use of any exposed service, network administrator, or other account credentials.
    3. Look for widespread scans of printers, largely across TCP port 443, after the threat actor establishes a foothold.
    4. Review for LDAP queries attempting to enumerate domain controller objects and services, including:
      1. servicePrincipalName=*cert*
      2. servicePrincipalName=*pki*
      3. servicePrincipalName=*public*
      4. objectclass=*
    5. Review for tampering with informational syslogs.
      1. Review for tampering or suppression of the following informational syslogs:
        1. 302013 (VPN connection established)
        2. 302014 (VPN connection terminated)
        3. 710005
        4. 609002
      2. If 302013 and 302014 are absent when expecting VPN activity, treat this as suspicious and investigate for potential threat actor malware.
      3. Examine historical trends for 302013 and 302014 (i.e., sudden gaps or cessation) to establish a potential tampering timeline.

      2. Copy and save the full output and off the device (preferably to an isolated system).
      3. Wait at least five minutes, then run “show checkheaps” again. Review the last row for “Total number of runs.”
        1. Expect an increase of approximately one per 60 seconds elapsed (i.e., if the command is executed five minutes apart, the number should increase by approximately five).

    Note: The steps below trigger an immediate reload of the device and may cause network degradation or outages.

    1. Soft reboot the device to maximize the likelihood of a clean core dump.
    2. Prepare to collect a core dump.
      1. Run the following commands to configure the device to generate a core dump:
        1. config t

        2. coredump enable filesystem <filesystem>

          Note: <filesystem> is typically “disk0:”

          However, not all Firepower devices will have the ability to run the coredump enable filesystem command. In those cases, entities should skip and proceed to the next step.

    3. Collect a core dump and save a copy.

      1. See Appendix A in the Cisco Firepower 1000/2100 Series Forensic Data Collection Procedures for consistent, model-agnostic instructions to obtain a core dump from Firepower 1000/2100/4100/9300 and Secure Firewall devices with ASA software.

        Note: FCEB agencies should contact CISA with any issues; for Firepower 4100/9300 devices removed from the network, coordinate with CISA to obtain the core dump.

    4. If nothing is written (i.e., no file appears in the file system):
      1. Record this condition.
      2. Review the command output for errors (i.e., “disk0: free space is too full to write a coredump.”)

      3. Run the commands again.

        1. If successful on the second attempt, inform CISA.
        2. If there is still no output, document and inform CISA; this may indicate an error or possible compromise.

        Note: Core dump files typically follow a naming pattern similar to: 

        1. “core_smp.2025Sep16_165718.1575.11.gz”
        2. “core.lina.16412.1756344191.gz”

        A “coredumpfsysimage.bin” file may also appear; however, this is not a core dump. It is a binary used during the process of dumping the memory out to a file and should not be uploaded.

    5. Run the following commands to capture the text segment memory dump, compute its SHA-512 hash, and transfer it off the device:
      1. show version | inc Version
      2. verify /sha-512 system:memory/text
      3. copy system:memory/text ftp
    6. After transferring the file from the device, CISA recommends recalculating the SHA-512 hash and comparing it to the value generated by command ii (verify /sha-512 system:memory/text).
    7. If the device crashes after running these commands, document the incident and inform CISA, as this behavior could be an indicator of compromise.

Save the output in a location off of the device. If your device crashes as a result of running any command in this step (excluding the expected reload during core dump collection), stop all actions and contact CISA immediately.

    1. Run “show checkheaps” command.
      1. Confirm and notate the time of the last successful checkheaps command.
      2. Copy and save the full output off the device (preferably to an isolated system).
      3. Wait at least five minutes, then run “show checkheaps” again. Review the last row for “Total number of runs.”

        1. Uptime

      2. Save the full output off the device (preferably to an isolated system).
    3. Check for the presence of the threat actor’s implant by running the following command: more /binary system:/text | grep 55534154 41554156 41575756 488bb3a0.
      1. Copy and save the full output off the device (preferably to an isolated system).
      2. Any output from this command is an indicator of compromise.
  2. Collect Core Dump

    Note: The steps below trigger an immediate reload of the device and may cause network degradation or outages.

    1. Soft reboot the device to maximize the likelihood of a clean core dump.
    2. Prepare to collect a core dump.
      1. Run the following commands to configure the device to generate a core dump:
        1. config t

        2. coredump enable filesystem <filesystem>

          Note: <filesystem> is typically “disk0:”

    3. Collect a core dump and save a copy.
      1. Initiate a core dump using the following command:
        1. crashinfo force page-fault
      2. Once the device reboots, transfer the zipped core dump file from the system to an external storage using one of the below commands.

        1. If the device is still connected to the network, use:

          copy disk0:/coredumpfsys/<filename.gz> [scp:/ftp:/tftp:]

        2. If the device has been disconnected or isolated from the network, save on a removable storage device or external laptop or device.

          1. To save on a removable storage device, use:

            copy disk0:/coredumpfsys/<filename.gz>disk1:/<filename.gz> 

            Note: The storage device must be FAT32 formatted for the Cisco device to utilize it properly.

          2. To save on an external laptop or device, use: 

            copy disk0:/coredumpfsys/<filename.gz> scp://username@192.168.0.1/path/to/file/<filename.gz> 

    4. If nothing is written (i.e., no file appears in the file system):
      1. Record this condition.
      2. Review the command output for errors (i.e., “disk0: free space is too full to write a coredump.”)

      3. Run the commands again.

        1. If successful on the second attempt, inform CISA.
        2. If there is still no output, document and inform CISA; this may indicate an error or possible compromise.

        Note: Core dump files typically follow a naming pattern similar to: 

        1. “core_smp.2025Sep16_165718.1575.11.gz”
        2. “core.lina.16412.1756344191.gz” 

        A “coredumpfsysimage.bin” file may also appear; however, this is not a core dump. It is a binary used during the process of dumping the memory out to a file and should not be uploaded.

    5. Run the following commands to capture the text segment memory dump, compute its SHA-512 hash, and transfer it off the device:

      1. show version | inc Version
      2. verify /sha-512 system:memory/text
      3. copy system:memory/text ftp

      Note: After transferring the file from the device, CISA recommends recalculating the SHA-512 hash and comparing it to the value generated by command ii (verify /sha-512 system:memory/text). If the device crashes after running these commands, document the incident and inform CISA, as this behavior could be an indicator of compromise.

B. Upload Core Dump in CISA’s Malware Next Generation (MNG) Platform

To upload a core dump to CISA’s MNG platform, see the Annex below.

C. Apply Patch per CISA’s ED 25-03 and Cisco’s Public Release and Security Advisory

After device artifact and core dump collection, apply Cisco’s latest software updates and consult the instructions in ED 25-03, Cisco's previous Public Release, and latest Security Advisory.

In alignment with Cisco’s guidance, organizations applying the patch to Cisco ASA devices should take the following actions: 

  1. Monitor console output during the device’s initial boot (as part of the update).

    1. Expected messages:

      Message #113 : Verifying bootloader: Message #114 : .Message
      #115 : .Message #116 : .Message #117 :
      Bootloader verification succeeded.
      Message #118 : Verifying ROMMON: Message #119 : .Message #120 :
      .Message #121 :
      .Message #122 : .Message #123 :
      ROMMON verification succeeded.
    2. If the expected “verification succeeded” messages appear, the persistence mechanism associated with this threat activity is likely not present.
    3. If the messages differ (i.e., “Bootloader verification failed at address” or “ROMMON verification failed at address”), this may indicate the persistence mechanism is present.
  2. Conduct a post-update check.
    1. For ASA 5512-X, 5515-X, 5525-X, 5545-X, 5555-X, or 5585-X devices updated to ASA 9.12.4.72 or 9.14.4.28, check disk0: for a file named firmware_update.log.
    2. The presence of firmware_update.log may indicate the threat actor compromised the device prior to the update.
D. Conduct Further Threat Hunting

If CISA’s MNG platform results show malicious indicators of compromise, disk0: contains the firmware_update.log file, or device messages during the update varied from the expected messages:

  • FCEB agencies should follow ED 25-03 and contact CISA immediately.
  • Other U.S. organizations should contact CISA via the Incident Reporting System or through CISA’s 24/7 Operations Center (contact@cisa.dhs.gov or 888-282-0870).
  • Cisco customers should open a Cisco Technical Assistance Center (TAC) case and include the output of the “show tech-support detail” command and the content of the firmware_update.log file.

In conjunction with Cisco’s released guidance, use the steps below to detect additional malicious activity, as the threat actor may have pivoted from the compromised device to other areas of the network. Organizations do not need to complete these steps strictly in order; however, begin with identifying compromised user accounts, which has proven the most reliable starting point.

  1. Identify Compromised Accounts

    Begin by identifying potentially compromised accounts. Based on current investigations, one reliable method is monitoring and searching for impossible-travel logins; scrutinize all logins traversing the compromised device.

    1. Monitor and search for impossible-travel logins.

      1. Detect suspicious logins from geographically distant IP addresses using the following Splunk Search Processing Language (SPL) query (tailor it to the security information and event management [SIEM] solution in place):

        index=<NDR/Appliance> sourcetype=<log_source>

        | search event_type="authentication"

        | iplocation src_ip

        | stats earliest(_time) AS first_login latest(_time) AS last_login by user, src_ip, City, Country

        | where first_login != last_login AND distance_between(first_login_location, last_login_location) > 1000

        | table user, src_ip, first_login, last_login, City, Country

    2. Review syslog message IDs.
      1. Informational level:
        1. WebVPN session terminated: Idle Timeout : %ASA-6-716002

      2. Debug level:

        1. SVC Service Termination: %ASA-7-722029
        2. SVC Service Termination: %ASA-7-722030
        3. SVC Service Termination: %ASA-7-722031

        Note: Informational-level syslogs should be enabled by default; enable if disabled. Debug-level syslogs are not enabled by default; enable if feasible.

  1. Review Compromised Account Activity

    Monitor and search for the below known threat actor activities conducted after obtaining account access.

    1. Check for credential reuse.
      1. If a compromised device contains user or service account credentials (i.e., usernames and passwords), assess those accounts for lateral movement, especially where credentials are reused across the enterprise or follow predictable patterns (e.g., “Password12 > Password23”).
      2. If only account names (no passwords) are present, enable enhanced monitoring (i.e., login sources, actions performed) and review for suspicious activity.
      3. If a compromised device provides virtual private network (VPN) access, search for login attempts from the assigned VPN pool address and compare against all authentication sources, regardless of the account used.
    2. Check for credential harvesting.
      1. Run a “show capture” command to check for evidence of unauthorized packet captures configured to target:
        1. Terminal Access Controller Access-Control System Plus (TACACS+)
        2. Remote Authentication Dial-In User Service (RADIUS)
        3. Lightweight Directory Access Protocol (LDAP)
        4. Server Message Block (SMB)
      2. Determine whether shared keys between the compromised device and the centralized authentication server could enable decryption of captured traffic; if so, monitor for unauthorized use of any exposed service, network administrator, or other account credentials.
    3. Look for widespread scans of printers, largely across TCP port 443, after the threat actor establishes a foothold.
    4. Review for LDAP queries attempting to enumerate domain controller objects and services, including:
      1. servicePrincipalName=*cert*
      2. servicePrincipalName=*pki*
      3. servicePrincipalName=*public*
      4. objectclass=*
    5. Review for tampering with informational syslogs.
      1. Review for tampering or suppression of the following informational syslogs:
        1. 302013 (VPN connection established)
        2. 302014 (VPN connection terminated)
        3. 710005
        4. 609002
      2. If 302013 and 302014 are absent when expecting VPN activity, treat this as suspicious and investigate for potential threat actor malware.
      3. Examine historical trends for 302013 and 302014 (i.e., sudden gaps or cessation) to establish a potential tampering timeline.

Annex: CISA MNG Platform Submission Instructions

MNG Submission Instructions

To upload a core dump to CISA’s Malware Next Generation (MNG) platform, you must have a login.gov account and MNG account.

User Types 

  • Government users: registering with an email ending in .gov or .mil.
  • Non-government users: registering with an email not ending in .gov or .mil. 

If you do not have a login.gov account, complete Create Your MNG Account below. If you are an existing MNG user, proceed to Submit a Core Dump Sample for Analysis.

Create Your MNG Account

  1. Using a web browser, go to https://malware.cisa.gov.
  2. Select “Create an Account” and follow instructions to create a login.gov account. Your login.gov account is used to access MNG and submit core dump samples for analysis.
  3. After creating your login.gov account, the webpage will redirect you to the MNG registration page. Provide your contact information. CISA uses this information only to provide support, if needed. It will not be shared outside of CISA.

  4. After registration, the webpage will redirect you to the MNG homepage, where you can view submissions and submit samples. It may take a moment for the system to assign permissions to your account. If you see a message stating you do not have permission to access the webpage, wait briefly and refresh.

Submit a Core Dump Sample for Analysis

  1. Click “Submit” in the blue banner at the top of the page.
  2. In “Upload Type,” select “File.”
  3. Click “Browse,” navigate to the saved core dump file, and select it.
    1. Core dumps from Firepower or Secure Firewall devices must remain in compressed GZ file format to avoid exceeding file size limits.
    2. Do not package the core dump in additional archive formats.
    3. Submit one core dump per submission. To submit multiple core dumps, repeat these steps for each file.
  4. Verify the selected file name appears next to the file selector.
  5. If you are registered with .gov or .mil account, check the “Core dump” box.
    1. Non-government users can only submit core dumps and will not see a sample-type selection.
  6. Select the device type (ASA or Firepower/Secure Firewall) from “Select Device Type.”
  7. Select the model series from “Model Series #.”
  8. For government users, select the appropriate Traffic Light Protocol (TLP) category.
    1. CISA treats all non-government submissions as TLP:AMBER+STRICT and will not share the submissions outside of CISA.
  9. In the “Comments Section,” include:
    1. Device serial number.
    2. Any errors or issues encountered during core dump collection.
    3. Any additional relevant comments.
  10. Check the box to agree to the MNG Terms of Service, Privacy Act Statement, and CISA’s Privacy Policy.
  11. Check the box to acknowledge submission agreement.
  12. Click “Submit.” Upload time will vary with file size and network speed. Upon completion, you will receive an on-screen confirmation:

Once submitted, analysis may take several minutes to complete.

To submit another core dump, select “Submit Another” and repeat the process. To review submissions, select “View all Samples” to return to the homepage and see analysis results.

Viewing Analysis Results

  1. The MNG homepage lists each submission with the date and time of submission.
  2. For valid core dumps, the “Verdict” column will display “Clean” or “Malicious.”
    1. If the scan failed, the “Status” column will display “Failed” and the “Verdict” column will display an “N/A” result.
  3. For detailed results, expand the entry (arrow to the left of the timestamp) and click the Transaction ID (TID).
  4. Under “Download Reports,” review the COREANALYSIS_RESULT file.
    1. If the report indicates “CLEAN: 1,” FCEB agencies should refer back to the relevant section and CISA’s ED 25-03.
    2. If the report indicates “DETECTED RAYINITIATOR: 1” or “DETECTED FIRESTARTER: 1,” contact CISA immediately. Do not proceed or take further action until you receive guidance from CISA Threat Hunting.
    3. If the report indicates “FAILED: 1,” results are inconclusive. FCEB agencies should contact CISA for assistance. Users can find additional details on failed scans in the COREANALYSIS_LOG file.

After completing MNG submissions, refer to the relevant sections of this document based on your device type(s).
